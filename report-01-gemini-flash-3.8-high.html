Empirical Findings & Key Insights

The goal of this evaluation is to determine how modern LLMs approach concurrent multi-subscriber distribution in Go when challenged to evolve the baseline ChanCaster and ChanPubSub designs from prompt 02. Across 18 distinct responses, models produced 31 distinct concrete implementations spanning four concurrency paradigms.

1. The Synchronous Rendezvous Scalability Barrier: The original baseline (ChanPubSub) delivers strict lossless rendezvous guarantees with zero heap allocations on publish. However, its reliance on individual per-subscriber channel handoffs imposes an inescapable O(N) overhead. At 1 subscriber, publication completes in 485.4 ns. At 256 subscribers, publication takes 554,198 ns (over half a millisecond). ChanGathererPubSub (05-Qwen) and ChanRotor (17-Gemini) exhibit identical O(N) slopes.

2. Channel-Close Multicast Wakeup as True O(1) Fanout: Go provides exactly one O(1) multicast broadcast primitive in the runtime scheduler: closing a channel. GenCaster (06-Meta) and ChanBeacon (07-Qwen) exploit this property. GenCaster replaces an atomic generation pointer and closes the previous generation channel. It achieved 57.4 ns at 1 subscriber and remained practically flat at 226.1 ns at 256 subscribers—a 2,451× throughput advantage over synchronous rendezvous at scale.

3. Lock-Free Circular Ring Logs for Zero-Alloc Throughput: RingPubSub (18-ChatGPT) achieved the highest overall throughput among full pub/sub systems. By combining a fixed power-of-two circular buffer, atomic acquire-release cursors, and selective notification, it achieved 135.6 ns/op at 4 subscribers with 0 bytes allocated and 0 heap allocations per send.

4. The Reality Gap in LLM Concurrency Implementations: While models proposed advanced theoretical mechanisms (seqlocks, lock-free wait-free queues, two-phase commits), nearly 40% of the raw outputs contained severe runtime bugs:

  • ChanGathererPubSub (05-Qwen) deadlocked on the second message due to desynchronized WaitGroup accounting and used an invalid RLock() on a sync.Mutex.
  • EpochTape (10-Gemini) implemented a seqlock that triggered Go race detector violations on multi-word reads and suffered variable reset defects during missed-slot retry loops.
  • Condition variable snapshot adapters suffered subtle race conditions when checking sub.Ready() and sub.Consume() out of order.

Taxonomy of Broadcast Concurrency in Go

Broadcasting in Go exists in tension between language primitives and hardware reality. Channels are point-to-point rendezvous queues designed for pipeline concurrency, not fan-out multicast. Across all evaluated responses, implementations cluster into four distinct structural paradigms:

1. Synchronous Rendezvous

Implementations: ChanCaster, ChanPubSub, ChanGathererPubSub, ChanPubSubV2, ChanPubSub09/10/14/16/17, ReliableBeacon.

Mechanism: Sender directly pushes to each subscriber channel or coordinates parallel fan-out goroutines with a dual WaitGroup (ping/pong) barrier.

Guarantees: Strictly lossless, exact delivery, zero memory allocation during broadcast.

Bottleneck: O(N) context handoffs. A single slow receiver or blocked goroutine immediately stalls the entire broadcast plane.

2. Lock-Free Circular Ring Logs

Implementations: RingPubSub, ChanLatest, ChanFeed, ChanFanout, ChanRotor, ChanRelay.

Mechanism: Data is written into a contiguous circular array indexed by monotonic 64-bit sequence numbers. Subscribers track local cursors independently.

Guarantees: Decoupled sender and receiver throughput. Zero heap allocation per message when capacity is sufficient.

Bottleneck: Buffer overrun policy. If slow consumers fall behind, systems must either block the sender or discard messages (drop oldest/newest).

3. Epoch Channel-Close Cascades

Implementations: GenCaster, EpochTape, ChanBeacon, Beacon, EpochCasterGemini, EpochPubSub11, EpochCaster13.

Mechanism: Exploits the runtime property that close(ch) broadcasts an immediate receive event to all listening goroutines simultaneously. The sender closes the current generation channel and atomically installs a new one.

Guarantees: True O(1) scheduler fan-out latency. Unaffected by the number of active subscribers.

Bottleneck: Requires 1 heap allocation per send (~96 bytes for a new channel), or complex seqlock synchronization for data payload extraction.

4. Credit-Based Coordinated Relays

Implementations: PhasePubSub, RelayPubSub.

Mechanism: Avoids per-send channel allocations by managing an explicit credit and phase state machine across active consumers.

Guarantees: Zero heap allocations, predictable backpressure signaling, and explicit delivery acknowledgments.

Bottleneck: Phase coordination overhead. At high subscriber counts, atomic CAS contention on subscriber state masks benefits over circular rings.

Audit Log of Identified & Repaired LLM Defects

To establish an apples-to-apples empirical benchmark, all extracted implementations were compiled into a single package bigbuff and executed under the Go race detector (-race) and fuzzing harness. The following severe concurrency defects and compilation gaps were diagnosed and repaired:

Defect 1: 05-Qwen Mutex Method Undefined & Deadlock

Symptom: changatherer.go failed compilation with x.sendMu.RLock undefined (type sync.Mutex has no field or method RLock).

Root Cause: The model declared sendMu sync.Mutex but used sendMu.RLock() during subscription registration.

Correction: Changed sendMu to sync.RWMutex.

Defect 2: 05-Qwen Double Increment Desynchronization

Symptom: TestStandardHarness hung permanently on message 2.

Root Cause: Qwen added x.pong.Add(delta) in Subscribe() and also added x.pong.Add(subs) in Send(), while omitting x.ping.Add(subs) in Send(). Because the underlying ChanCaster resets counts on send completion, the second broadcast waited for pongs that were never released.

Correction: Corrected Send() to manage both ping and pong counters and cleaned Subscribe() to only track subscriber counts.

Defect 3: 10-Gemini EpochTape Seqlock Data Race

Symptom: go test -race detected data races on multi-word struct access between slot.val = value in Publish() and val := slot.val in TryNext().

Root Cause: In Go's memory model, seqlocks without compiler-enforced atomic slot loads cause word tearing on interfaces and multi-word types. Unsynchronized concurrent reads and writes trigger the race detector.

Correction: Protected slot read/write with a fine-grained sync.RWMutex per slot, preserving lock-free epoch checking while ensuring race-free value transfer.

Defect 4: 10-Gemini EpochTape Missed-Message Loss on Retry

Symptom: TestEpochTape_BroadcastAndSelect deadlocked when running 128 subscribers.

Root Cause: In TryNext(), var skipped uint64 was declared inside the retry loop. Whenever a seqlock collision or lag occurred, skipped was reset to 0, discarding previously counted drops and causing tests to block waiting for values that were never delivered.

Correction: Declared var totalMissed uint64 outside the retry loop to accumulate missed message counts across retry iterations.

Defect 5: 14-Xing Missing Private Helper Methods

Symptom: chancaster_14_xing.go failed compilation with undefined methods checkBroken, markBroken, sanityCheckSubscribersDelta.

Root Cause: The model truncated the implementation with placeholder comments (// ... other private helpers are unchanged).

Correction: Implemented the missing private helper methods in full conforming to the model's specified state invariants.

Defect 6: Condition Variable Notification Race in Subscriber Adapters

Symptom: BenchmarkUnified_Select deadlocked intermittently on ChanBeacon, EpochTape, and ChanFeed.

Root Cause: Calling sub.Consume() followed by select { case <-sub.Ready(): } created a race window. If the publisher broadcasted and closed the ready channel after Consume() but before Ready() was called inside select, the consumer captured the next (open) channel and blocked indefinitely.

Correction: Enforced the canonical snapshot pattern: capture ready := sub.Ready() before checking Consume(), ensuring that any send occurring during the check will fire the captured ready channel immediately.

Defect 7: RingSubscription Lock-Copy in Standard Harness

Symptom: go vet ./... failed with literal copies lock value from sub: bigbuff.RingSubscription[int] contains bigbuff.ringPubSubNoCopy.

Root Cause: RingSubscription embeds ringPubSubNoCopy with Lock() and Unlock() methods specifically to enforce address-based ownership transfers. ringPubSubSub in harness_test.go stored the subscription struct by value rather than by pointer.

Correction: Updated ringPubSubSub to store *RingSubscription[int] and pass by reference, satisfying go vet and adhering to the no-copy cursor contract.

Defect 8: Synchronous Rendezvous Barrier Deadlock in Fuzz Harness

Symptom: go test -race . hung permanently on FuzzUnifiedBroadcaster/seed#2.

Root Cause: ChanPubSub is an unbuffered rendezvous barrier broadcast requiring all registered subscribers to actively consume concurrently in separate goroutines. The fuzz harness sequentially invoked operations on a single goroutine; when two subscribers were registered and only one received, that subscriber blocked in Wait() waiting for the publisher, while the publisher blocked sending to the unread subscriber on the unbuffered channel.

Correction: Constrained FuzzUnifiedBroadcaster to circular ring/tape/queue broadcasters with decoupled per-subscriber cursors, documenting that rendezvous barrier implementations require concurrent goroutine consumers.

Defect 9: Unsynchronized Ring Buffer Overwrite Data Race in 07-Qwen ChanBeacon

Symptom: go test -race -bench=BenchmarkUnified_Broadcast detected a data race on b.buf[idx] between ChanBeacon.Send() and RelaySub.Consume().

Root Cause: 07-Qwen relied solely on atomic acquire-release on the write cursor (head) to synchronize buffer reads. Under consumer lag or wrap-around, the publisher overwrites a ring slot while a lagging consumer is still reading that slot, causing concurrent unsynchronized slice access.

Correction: Added fine-grained slotMu []sync.RWMutex to ChanBeacon, guarding slot read/write during wrap-around and overrun while keeping the public API signatures completely unchanged.

Defect 10: Deferred Context Cancellation Causing 14s Stalls in Churn Harness

Symptom: TestStandardHarness_ConcurrentChurn took over 14 seconds to execute, stalling for exactly 2.00s per broadcaster.

Root Cause: In TestStandardHarness_ConcurrentChurn, cancel() was deferred until test exit (after wg.Wait()). When stop.Store(true) was signaled, subscribers parked in s.Receive(ctx) waited for the full 2-second timeout before exiting.

Correction: Invoked cancel() immediately upon setting stop.Store(true) prior to wg.Wait(), unblocking parked subscriber goroutines instantly and reducing runtime from 14.41s to 0.75s.
